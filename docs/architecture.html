Del lector de solo lectura a una herramienta con modos

Hoy la aplicación lee y revisa desarrollos de muchos repositorios sin escribir nunca en ellos. Este documento repasa cómo está hecha, dónde se va a romper cuando lleguen modos nuevos (usos, comentarios, edición) y propone una estructura por módulos y una migración por fases que no rompe nada por el camino.

1. Lo que hay hoy

Cuatro paquetes bajo internal/ y un main.go que lee las opciones y abre la ventana. Las dependencias van hacia abajo y no hay ciclos: app usa review, git y highlight; review usa git y highlight.

Dónde está el acoplamiento

  • App lo sabe todo. Un struct con unos 25 campos: proyectos, cachés de documentos y de tipos de clase, el estado de la barra lateral, del editor, del buscador y del diálogo de base, el foco, el tema, los atajos y los avisos. Los paneles se manejan desde fuera: app.go, build.go y reviewing.go tocan 70 veces el estado de sidebar, editor o finder, y los paneles reciben App entero (sidebar.revealFile(application, …)).
  • Los modos son un enum. filesMode y reviewMode se deciden con if en setMode, en la barra lateral y en el editor (fileView / diffView). Un tercer modo toca los tres archivos.
  • Los atajos son un único switch. handleKeys tiene 22 casos y la ayuda se escribe aparte a mano. Un modo nuevo no puede traer sus teclas ni saber cuáles están libres.
  • Cada archivo de panel mezcla cuatro cosas: estado, entrada, maquetación y pintado. sidebar.go (753) y editor.go (675) son los más grandes.
  • Lo específico de Java está repartido entre review/javatree.go, app/classes.go y el pintado de la barra lateral. Kotlin, TypeScript o .NET repetirían el reparto.
  • El trabajo en segundo plano es artesanal. later() manda funciones por un canal y la búsqueda de contenido lleva su propio contador de generación para descartar resultados viejos. No hay cancelación ni prioridades.
  • Solo lectura por convención de un sitio. La garantía es la lista blanca de git/run.go. Es buena, pero un modo que escriba no tendría dónde pedir permiso: habría que aflojar la lista, que es justo lo que no queremos.

2. Qué tiene que permitir la arquitectura

Modos previstos
  • Archivos y Revisión: los de hoy.
  • Usos: pulsar una clase o un método y ver dónde se usa; primero con git grep, después con un servidor de lenguaje (LSP).
  • Comentarios: anotar líneas; en local o en el PR de Azure DevOps / GitHub.
  • Edición: arreglar algo pequeño sin salir del lector.
Reglas que no cambian
  • Abrir un repositorio nunca lo modifica. Escribir es un permiso explícito, por modo y por repositorio.
  • push no existe dentro de la aplicación.
  • Rápida con 44 repositorios: nada bloquea el fotograma.
  • Cada modo se prueba solo con uitest.

4. Las piezas clave

Modo

Un modo declara lo que necesita y lo que aporta. El shell lo pone en la barra de modos, une sus comandos al registro y le pide qué mostrar; no hay if mode == en ningún panel.

type Mode interface {
    ID() string                        // "files", "review", "usages"…
    Title() string
    Icon() string
    Needs() policy.Capabilities        // Read, Marks, Comment, WriteTree
    Sidebar(*core.Workspace) panes.TreeSource   // qué filas y con qué marcas
    Present(*core.Document) panes.Presentation  // archivo entero, diff o anotado
    Commands() []shell.Command         // con sus teclas y contexto
    Status(*core.Workspace) []shell.StatusItem
}

Lectura y escritura separadas

La lista blanca de hoy pasa a ser el git.Reader, sin cambios. Escribir es otra interfaz, con otro ejecutor y su propia lista (add, commit; nunca push), y solo se obtiene a través de policy. Un Reader no puede convertirse en Writer: son tipos distintos, no el mismo con un flag.

type Reader interface {
    Changes(base string, workingTree bool) ([]core.Change, error)
    Diff(path string) ([]core.DiffLine, error)
    ReadFile(ref core.Ref) ([]byte, error)
    Grep(text string, options GrepOptions) ([]Hit, error)
}
type Writer interface {          // solo vía policy.Grant
    WriteFile(path string, content []byte) error
    Stage(paths ...string) error
    Commit(message string) error
}
// Grant pregunta una vez por repositorio y modo, y lo recuerda solo esta sesión.
func (p *Policy) Grant(project *core.Project, mode string, need Capability) (vcs.Writer, error)
Por qué así

Con -read-only (por defecto) el escritor ni se construye y Grant siempre dice que no. Los modos de hoy declaran Read y Marks, y las marcas viven en la carpeta de la aplicación, no en el repositorio. Sigue siendo imposible escribir en un repositorio sin un clic explícito del usuario.

Comandos y atajos

Cada acción es un comando con nombre, contexto y tecla: {ID: "review.markViewed", Key: "v", When: "mode=review"}. El registro detecta choques al arrancar, la ayuda (?) se genera de él y el buscador puede ofrecer también comandos. handleKeys desaparece.

Paneles como componentes

go-ui es de modo inmediato, así que un componente no es un objeto vivo: es un struct de estado más tres funciones. Los paneles no se llaman entre sí; publican eventos (FileOpened, ModeChanged, RevealRequested) y el shell los reparte al empezar el fotograma.

type Pane interface {
    Handle(shell.Input, *shell.Events) // teclas y ratón ya filtrados por foco
    Build(*ui.Context)                 // maquetación
    Paint(area draw2d.Rectangle, *draw2d.List)
}

Tareas en segundo plano

tasks.Run(key, work) sustituye a later() y al contador de generación de la búsqueda: una tarea nueva con la misma clave cancela la anterior (vía context.Context), el resultado llega al hilo del fotograma y pide uno nuevo. Mantiene el límite de 6 lectores y el modo síncrono para capturas y tests.

Lenguajes

Lo que hoy es de Java se vuelve un proveedor: lang.Language dice si reconoce un proyecto, cómo agrupa su árbol (módulos, raíces, paquetes) y qué declara cada archivo. Los usos con LSP entran por aquí: el proveedor de símbolos arranca jdtls sobre un clon APFS en la caché de la aplicación, nunca sobre el repositorio.

6. Migración por fases

Cada fase es un commit que compila, pasa los tests y deja la aplicación igual para quien la usa. Se puede parar en cualquiera.

0

Fijar el comportamiento

Ampliar app_test.go: cada atajo de cada modo, abrir, marcar visto, entrar en un proyecto, buscar. Es la red para todo lo demás.

1

Partir review

Mover a core, store, search/names y lang/java. Solo cambian imports.

2

Tareas

tasks en lugar de later() y del contador de la búsqueda; cancelación por clave.

3

Comandos y atajos

Registro con contexto; la ayuda sale de él. handleKeys se vacía caso a caso.

4

Paneles y eventos

Árbol, visor y buscador como componentes; App queda como shell más workspace.

5

Interfaz de modo

Archivos y Revisión pasan a modes/. A partir de aquí, un modo nuevo no toca los paneles.

6

Puertos de VCS y permisos

vcs.Reader y policy. El escritor aún no existe; solo su interfaz y el «no» por defecto.

7

Primer modo nuevo: Usos

Con git grep en todos los repositorios; después LSP sobre clones APFS. Sirve de prueba de que las fases 3–5 funcionan.

7. Decisiones pendientes

PreguntaPropuesta
¿Qué modo nuevo va primero?Usos: es de solo lectura y prueba la arquitectura sin abrir la puerta de la escritura.
¿Dónde viven los comentarios?Primero en local (store); un adaptador a Azure DevOps o GitHub después, con su propia capacidad Comment.
¿Edición en el repositorio o en un worktree?En un git worktree aparte, creado con permiso; el repositorio revisado no se toca.
¿Cuándo hacer la migración?Fases 0–5 antes de cualquier modo nuevo; son mecánicas y los tests de la fase 0 las cubren.
